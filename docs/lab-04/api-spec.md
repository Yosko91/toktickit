# Lab 4 REST API Specification

Base URL `http://localhost:3000`. Extends `docs/lab-03/api-spec.md`. Authentication is the same
session cookie as Lab 3 (`toktickit.sid`, httpOnly, SameSite=Lax). Every endpoint below needs a
valid session (`401` otherwise) and a completed password change (`403 PASSWORD_CHANGE_REQUIRED`
otherwise), like in Lab 3.

## 1. Error body and status codes

Same body as Lab 3, with one more optional field for conflicts:

```json
{ "error": "This item was changed by someone else. Reload it and try again.",
  "code": "STALE_UPDATE", "currentVersion": 4 }
```

| Status | Meaning in Lab 4 |
|---|---|
| 400 | Invalid input. `details` has one message per field. |
| 401 | No valid session. |
| 403 | Role not permitted (for example a Requester on a staff or action endpoint). |
| 404 | Ticket or action not found, or hidden because it belongs to another Requester. |
| 405 | Delete of an Action Taken (never deleted, BR-10). |
| 409 | Conflict. `code` tells which one: `STALE_UPDATE`, `INVALID_TRANSITION`, `ACTION_READ_ONLY`, `TICKET_NOT_WORKABLE`, `OWNER_REQUIRED`, `NO_COMPLETED_ACTION`, `OPEN_ACTIONS`. |
| 422 | Well formed but unusable reference: performer or owner who is not an active staff member. |
| 500 | Unexpected error. The message is generic, details only go to the server log. |

## 2. Shapes

### Action Taken

```json
{
  "id": 41,
  "ticketId": 7,
  "actionAt": "2026-10-26T03:15:00.000Z",
  "description": "Replaced the laptop battery with a new one from stock.",
  "result": "Battery holds charge for 6 hours in the test.",
  "status": "COMPLETED",
  "performedById": 9,
  "performedByName": "Michael Brown",
  "createdById": 9,
  "createdByName": "Michael Brown",
  "followUpRequired": true,
  "followUpNote": "Check again with the requester next week.",
  "attachmentNotes": "See battery-report.pdf in the ticket attachments.",
  "version": 1,
  "createdAt": "2026-10-26T03:20:11.000Z",
  "updatedAt": "2026-10-26T03:20:11.000Z"
}
```

`status` is one of `PLANNED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`. Names come from the joined
user rows, never from the request body.

### Status history item

```json
{ "id": 3, "fromStatus": "IN_PROGRESS", "toStatus": "RESOLVED",
  "changedById": 9, "changedByName": "Michael Brown", "changedAt": "2026-10-26T04:00:00.000Z" }
```

### Ticket Detail additions

`GET /api/tickets/:id` (Requester view) and `GET /api/staff/tickets/:id` (staff view) both add:

```json
{
  "version": 3,
  "resolvedAt": null,
  "actionsTaken": [ "...Action Taken shape, ordered by actionAt asc, then id asc (BR-15)" ],
  "statusHistory": [ "...history items, ordered by changedAt asc, then id asc (BR-20)" ]
}
```

The Requester view gets all Actions Taken of the Ticket (FR-05). It still never contains Internal
Notes (L3-BR-26). A legacy Ticket returns `"actionsTaken": []` and `"statusHistory": []` (BR-34).

## 3. Actions Taken endpoints (IT Staff and Administrator)

All three are under the Lab 3 staff router, so a Requester gets `403` before anything is read
(BR-03).

### POST /api/staff/tickets/:id/actions

Body:

| Field | Type | Rule |
|---|---|---|
| `actionAt` | ISO date string | required, not before the Ticket creation, not in the future unless `PLANNED` (BR-07) |
| `description` | string | required, 1 to 2000 after trim (BR-05) |
| `result` | string or null | max 2000, required when status is `COMPLETED` (BR-09) |
| `status` | string | `PLANNED`, `IN_PROGRESS` or `COMPLETED`, default `COMPLETED` (BR-08). `CANCELLED` is refused at creation. |
| `performedById` | int or omitted | omitted means the session user. Must be an active staff user (BR-04) |
| `followUpRequired` | boolean | default false |
| `followUpNote` | string or null | required when `followUpRequired` is true, max 1000 (BR-06) |
| `attachmentNotes` | string or null | max 500 |
| `clientRequestId` | string | 8 to 100 characters, generated by the client once per form (BR-14) |

Responses:

| Status | When |
|---|---|
| 201 | Created. Body is the Action Taken. `createdById` is the session user. |
| 200 | Same `clientRequestId` already used on this Ticket: the existing action is returned, nothing new is created. |
| 400 | Validation, `details` per field. |
| 404 | Ticket not found. |
| 409 | `TICKET_NOT_WORKABLE` (Ticket is Resolved, Closed or Cancelled, BR-11), or the `clientRequestId` was already used on another Ticket. |
| 422 | `performedById` is not an active IT Staff or Administrator user. |

### PATCH /api/staff/tickets/:id/actions/:actionId

Body: `version` (required, the version the client read) and any fields from the table above.
The rules are checked on the action as it will be after the change, so for example completing an
action that has no result needs a `result` in the same request.

Checks are done in this order: action belongs to this Ticket (`404`), `version` present (`400`),
`version` current (`409 STALE_UPDATE`), action not finished (`409 ACTION_READ_ONLY`), Ticket
workable (`409 TICKET_NOT_WORKABLE`), field rules (`400`), status move permitted (`409
INVALID_TRANSITION`), performer (`422`). The save itself is
`UPDATE ... WHERE id = :actionId AND version = :version`, so two saves on the same version cannot
both win: the second gets `409 STALE_UPDATE`.

`200` returns the action with `version` increased by one. `createdById` never changes.

Permitted status moves (BR-08): `PLANNED` to `IN_PROGRESS`, `COMPLETED`, `CANCELLED`;
`IN_PROGRESS` to `COMPLETED`, `CANCELLED`. Sending the same status as now is not a move and is
allowed (edit of the other fields).

### DELETE /api/staff/tickets/:id/actions/:actionId

Always `405` with `"Actions Taken are never deleted. Cancel the action instead."` (BR-10).

## 4. Ticket workflow changes (Lab 3 endpoints)

### PATCH /api/staff/tickets/:id/status

Body `{ "currentStatus": "RESOLVED", "version": 3 }`. `version` is optional for Lab 3 callers and
always sent by the Lab 4 client (BR-22).

Order of checks: Ticket exists (`404`), status value valid (`400`), version current (`409
STALE_UPDATE`), move in the matrix (`409 INVALID_TRANSITION`), and for `RESOLVED` the gate (BR-18):
owner present (`409 OWNER_REQUIRED`), at least one completed action (`409 NO_COMPLETED_ACTION`),
no planned or in progress action (`409 OPEN_ACTIONS`).

On success the status update, the version increase, `resolvedAt` (set on Resolved, cleared on
Reopened) and the history row are written in one transaction. `200` body:

```json
{ "id": 7, "currentStatus": "RESOLVED", "version": 4, "resolvedAt": "2026-10-26T04:00:00.000Z" }
```

### PATCH /api/staff/tickets/:id/owner and PATCH /api/staff/tickets/:id/it-priority

Same as Lab 3, plus optional `version` in the body (`409 STALE_UPDATE` when it is old) and
`version` in the `200` body. The Lab 3 rules stay: owner must be active staff (`422`), Requested
Priority never changes.

## 5. List filters

`GET /api/tickets` (Requester, own Tickets) and `GET /api/staff/tickets` (staff queue) accept
`statusGroup=active`, which keeps only New, Open, In Progress, Waiting for Requester and Reopened
(BR-25). It can be combined with the other Lab 2 and Lab 3 filters. Any other value answers `400`.

## 6. Dashboard endpoints

Both return counts and short lists only (max 5 items per list, BR-32). Counts are calculated on
each request (BR-24). `generatedAt` is the server time used for the 30 day window (BR-30).

The short Ticket item used in the lists:

```json
{ "id": 7, "ticketNumber": "TKT-2026-000007", "summary": "Laptop battery drains quickly",
  "currentStatus": "IN_PROGRESS", "itPriority": "MEDIUM", "ownerName": "Michael Brown",
  "updatedAt": "...", "resolvedAt": null }
```

### GET /api/dashboard/requester

Requester only (`403` for other roles, BR-26). Only Tickets where `requesterId` is the session
user.

```json
{
  "generatedAt": "2026-10-26T05:00:00.000Z",
  "metrics": [
    { "key": "active",   "label": "My Active Tickets", "value": 3, "link": "/tickets?statusGroup=active" },
    { "key": "waiting",  "label": "Waiting for Me",    "value": 1, "link": "/tickets?currentStatus=WAITING_FOR_REQUESTER" },
    { "key": "resolved", "label": "Resolved",          "value": 1, "link": "/tickets?currentStatus=RESOLVED" },
    { "key": "closed",   "label": "Closed",            "value": 2, "link": "/tickets?currentStatus=CLOSED" }
  ],
  "needsAttention": [ "...own WAITING_FOR_REQUESTER, updatedAt asc" ],
  "recentlyUpdated": [ "...own, updatedAt desc, id desc" ],
  "recentlyResolved": [ "...own, resolvedAt in the last 30 days, resolvedAt desc" ]
}
```

Calculation (all with `requesterId = <session user>`):

| Metric | Query |
|---|---|
| active | `currentStatus IN (NEW, OPEN, IN_PROGRESS, WAITING_FOR_REQUESTER, REOPENED)` |
| waiting | `currentStatus = WAITING_FOR_REQUESTER` |
| resolved | `currentStatus = RESOLVED` |
| closed | `currentStatus = CLOSED` |

### GET /api/dashboard/staff

IT Staff and Administrator (`403` for a Requester).

```json
{
  "generatedAt": "2026-10-26T05:00:00.000Z",
  "metrics": [
    { "key": "unassigned",    "label": "Unassigned",      "value": 4, "link": "/queue?ownerId=unassigned&statusGroup=active" },
    { "key": "assignedToMe",  "label": "Assigned to Me",  "value": 2, "link": "/queue?ownerId=9&statusGroup=active" },
    { "key": "myOpenActions", "label": "My Open Actions", "value": 1, "link": "#my-open-actions" }
  ],
  "byStatus": [ { "status": "NEW", "value": 5, "link": "/queue?currentStatus=NEW" }, "...OPEN, IN_PROGRESS, WAITING_FOR_REQUESTER, REOPENED, RESOLVED" ],
  "byItPriority": [ { "priority": "HIGH", "value": 2, "link": "/queue?itPriority=HIGH&statusGroup=active" }, "...MEDIUM, LOW" ],
  "myOpenActions": [ { "id": 41, "ticketId": 7, "ticketNumber": "TKT-2026-000007", "description": "...", "status": "PLANNED", "actionAt": "..." } ],
  "urgentTickets": [ "...active and itPriority HIGH, createdAt asc" ],
  "recentlyUpdated": [ "...updatedAt desc, id desc" ],
  "userCounts": { "activeRequesters": 7, "activeItStaff": 3, "activeAdministrators": 2, "inactiveUsers": 2, "link": "/admin/users" }
}
```

`userCounts` is present only for an Administrator (BR-29). The My Open Actions card links to the
list on the same page, because there is no separate screen listing actions.

Calculation:

| Metric | Query |
|---|---|
| unassigned | `ownerId IS NULL AND currentStatus IN (active group)` |
| assignedToMe | `ownerId = <me> AND currentStatus IN (active group)` |
| myOpenActions | `ActionTaken.performedById = <me> AND ActionTaken.status IN (PLANNED, IN_PROGRESS)` and its Ticket in the active group |
| byStatus[s] | `currentStatus = s`, for the five active statuses and RESOLVED |
| byItPriority[p] | `itPriority = p AND currentStatus IN (active group)` |
| userCounts | `User.isActive = true` grouped by role, and `isActive = false` |
