# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver the Requester-facing ticketing MVP: a Requester (simulated through a temporary
Development Requester selector) can create an IT support ticket with a category, related
system, requested priority, description, and up to five attachments; receive a
backend-generated Ticket Number; find that ticket again in a searchable, filterable, sortable,
paginated My Tickets list; open a read-only Ticket Detail screen; and add or soft-remove
attachments on their own tickets. One Requester can never see or modify another Requester's
data. All screens follow one reusable Zen Green visual system.

## 2. Stakeholder Request Interpretation

IT wants a real intake channel for support requests before real login exists. Requesters need
to: describe a problem with enough structure (category, related system, priority) for IT to
triage it later; attach evidence (screenshots, PDFs); get a trackable ticket number; and later
find, review, and manage the attachments on their own tickets — without being able to see
anyone else's. Because authentication is a Lab 3 concern, Lab 2 simulates "who is asking" with
an explicit, clearly-labeled Development Requester selector so ownership rules can be built and
tested now.

## 3. Scope

### Included
- Development Requester Selection screen (testing mechanism) and Requester context.
- Create Ticket: form, validation, attachment selection, submission, Ticket Number display.
- My Tickets: owned ticket list with search, filter, sort, pagination, empty/no-results states.
- Requester Ticket Detail: read-only ticket fields + attachment list.
- Attachment lifecycle: upload, download, soft removal (with reason), metadata retention.
- Ownership enforcement on every Requester-scoped read/write.
- Zen Green Theme tokens and reusable form/list/badge/state components.
- Reference data: Category (existing), Related System (new), seeded Development Requesters.

### Excluded
- Authentication, sessions, passwords, tokens, real authorization (Lab 3).
- IT Staff dashboard/queue, claiming, IT Priority, Ticket Owner assignment.
- Public Comments, Internal Notes, Actions Taken.
- Any ticket status beyond the initial `NEW` (no resolve/close/reopen/cancel).
- Administrator functions (managing Requesters, roles, reference data via UI).

## 4. Functional Requirements

- FR-01 The system lets a Requester create a Ticket with Category, Related System, Summary,
  Description, Requested Priority, and optional Attachments.
- FR-02 The system generates and returns a unique Ticket Number on successful creation.
- FR-03 The system lets a Requester list only the Tickets they own, with search, category
  filter, priority filter, status filter, sorting, and pagination.
- FR-04 The system lets a Requester open the detail of a Ticket they own, read-only.
- FR-05 The system rejects retrieval of a Ticket or Attachment the current Requester does not
  own, without revealing whether it exists for someone else.
- FR-06 The system lets a Requester add an Attachment to a Ticket they own, subject to type,
  size, and count limits.
- FR-07 The system lets a Requester download an active (non-removed) Attachment they own.
- FR-08 The system lets a Requester soft-remove an Attachment they own by providing a reason;
  the Attachment's metadata remains visible but it can no longer be downloaded.
- FR-09 The system loads active Development Requesters for the selector and excludes inactive
  ones.
- FR-10 The system loads active Categories and active Related Systems for the Create Ticket
  form.
- FR-11 The system preserves the Requester's entered form values when Ticket creation fails,
  so nothing has to be retyped.
- FR-12 The system prevents duplicate Ticket creation from a single form submission (double
  click / repeated Enter).

## 5. Business Rules

### Ticket defaults and system-generated values
- BR-01 The official Ticket Number is generated by the backend, using the pattern
  `TKT-{creationYear}-{6-digit sequence}` (e.g. `TKT-2026-000042`), and is globally unique. It
  is produced from a dedicated PostgreSQL sequence so uniqueness holds under concurrent
  creation.
- BR-02 A new Ticket always begins with Current Status `NEW`. No other status is reachable in
  Lab 2.
- BR-03 Ticket Date (`createdAt`) is set by the backend at creation time and is never
  Requester-editable.
- BR-04 `updatedAt` is maintained by the backend and changes whenever the Ticket row changes
  (e.g. an Attachment is added or removed).

### Development Requester selection and switching (testing mechanism, not authentication)
- BR-05 Lab 2 uses a Development Requester selector instead of login. The selected identity is
  for testing only and is not authentication; the UI states this explicitly.
- BR-06 Only active Requesters (`isActive = true`) appear in the selector. Inactive Requesters
  cannot be selected.
- BR-07 The selected Requester id is kept in the browser's `sessionStorage` only (cleared when
  the tab closes) — never in a cookie, JWT, or server session — to keep the mechanism visibly
  distinct from real authentication.
- BR-08 Every Requester-scoped API request must carry the selected Requester id in the
  `X-Dev-Requester-Id` request header. Requests without it, or with an id that does not match
  an existing Requester, are rejected.
- BR-09 If the id in `X-Dev-Requester-Id` belongs to a Requester whose `isActive` has become
  `false`, the request is rejected (`403`) and the client clears its stored selection and
  returns to the Selection screen.
- BR-10 Switching Requester ("Change Requester") clears the current selection, returns to the
  Selection screen, and causes all Requester-owned data (My Tickets, any open Ticket Detail) to
  be reloaded, never reused, from the newly selected Requester.
- BR-11 If the active-Requester list fails to load, the Selection screen shows a safe failure
  state with a retry action and creates no session. If it loads but is empty, the Selection
  screen shows an empty state and blocks entry (no Continue is possible).

### Ticket ownership
- BR-12 A Ticket belongs to exactly one Requester (`Ticket.requesterId`), set once at creation
  from the header identity and never changed afterward.
- BR-13 A Requester may only list, view, or modify (add/remove Attachments on) Tickets they
  own. Any attempt on a Ticket owned by another Requester is treated as if the Ticket does not
  exist (`404`), not as a permission error, so ownership is never leaked by a `403`.

### Validation and duplicate-submission prevention
- BR-14 Ticket Summary is required, trimmed, and must be 5-120 characters after trimming.
- BR-15 Description is required, trimmed, and must be 20-2000 characters after trimming.
- BR-16 Category and Related System are required and must reference an existing, active row;
  an id for an inactive or unknown row is rejected.
- BR-17 Requested Priority is required and must be one of `LOW`, `MEDIUM`, `HIGH` (no default
  is silently assumed server-side; the UI pre-selects `MEDIUM` but the Requester can change it
  before submitting).
- BR-18 All validation above runs on both frontend (immediate field feedback) and backend
  (authoritative; the frontend check is never trusted alone).
- BR-19 The Submit control is disabled and shows a busy state from the moment a submission
  starts until a response (success or failure) is received, preventing duplicate Tickets from
  repeated clicks.

### Failure behavior and data retained after errors
- BR-20 If Ticket creation fails for any reason (validation, network, server error), the form
  keeps every value the Requester entered; only the failing field(s) show an error, or a
  general banner is shown for non-field failures (e.g. network/server down).
- BR-21 If the backend is unreachable, the UI shows a distinct "can't reach the server" failure
  state rather than a validation message, and offers Retry.

### Attachment upload, download, and soft removal
- BR-22 Allowed Attachment types are JPG/JPEG, PNG, WEBP, and PDF, checked by both file
  extension and MIME type; anything else is rejected before upload starts where possible, and
  rejected by the backend (`415`) otherwise.
- BR-23 Maximum Attachment size is 5 MB per file; larger files are rejected before upload where
  possible, and rejected by the backend (`413`) otherwise.
- BR-24 A Ticket may have at most five **active** (non-removed) Attachments. A sixth active
  upload attempt is rejected (`409`) with a clear message; removed Attachments do not count
  toward the limit.
- BR-25 Ticket creation and Attachment upload are two separate backend operations. If the
  Ticket is created but one or more selected Attachments fail to upload, the Ticket is **not**
  rolled back: it exists with its Ticket Number, and the Requester is shown exactly which
  file(s) failed and why, with the option to retry the upload from the newly created Ticket's
  screen (which is the Ticket Detail screen). This is the compensation strategy: no distributed
  transaction is attempted between the Ticket row and the file system.
- BR-26 Each Attachment stores required metadata: original filename (display only, sanitized),
  stored filename (a generated identifier, never derived from user input, used as the actual
  file on disk), MIME type, size in bytes, uploading Requester, and upload timestamp.
- BR-27 Removal is always soft: an Attachment row is never deleted. Removal sets `removedAt`,
  `removedReason` (required, 3-200 characters, trimmed), and `removedById`.
- BR-28 A removed Attachment remains visible in the Ticket Detail attachment list as metadata
  (name, size, type, upload date, removal date, removal reason) but its download and preview
  actions are disabled in the UI and rejected by the backend (`410 Gone`) if called directly.
- BR-29 Only the owning Requester of the parent Ticket may add or remove Attachments on it;
  this is the same ownership check as BR-13.

### Inactive Requesters
- BR-30 An inactive Requester never appears in the Selection screen dropdown (BR-06). Existing
  Tickets created by a Requester who is later made inactive are unaffected and remain visible
  under that Requester's id (there is no UI path to deactivate a Requester in Lab 2; the seed
  simply ships one inactive row to prove this rule is enforced end-to-end).

### Empty and no-results states
- BR-31 My Tickets shows a distinct **empty state** ("You haven't created any tickets yet" +
  Create Ticket action) only when the Requester owns zero Tickets in total (no filters
  applied). It shows a distinct **no-results state** ("No tickets match your filters" + Clear
  Filters action) when the Requester owns Tickets but the current search/filter combination
  matches none of them.

### Ticket Detail access
- BR-32 Ticket Detail is reachable only by a direct, owned Ticket id. There is no numeric or
  sequential guessing protection beyond ownership (BR-13): every id, owned or not, is checked
  against the current Requester on every request.

### Transition to real authentication (Lab 3)
- BR-33 The `X-Dev-Requester-Id` header and the Requester Selection screen are temporary. In
  Lab 3 they are replaced by a real session derived from an authenticated login; the
  `requesterId` foreign key on `Ticket` is designed to be populated from that session instead,
  with no schema change required.

## 6. UI Specification Summary

Full detail lives in `docs/lab-02/ui-spec.md`. Summary:
- **App shell**: TokTickIT header (primary green), My Tickets / Create Ticket nav, current
  Requester display with a Change Requester action, responsive hamburger nav under 992px.
- **Requester Selection**: title, one-sentence "testing only" notice, dropdown of active
  Requesters, Continue button, loading/empty/failure states.
- **Create Ticket**: system-generated fields (Ticket Number, Ticket Date, Requester) shown
  read-only near the top once available; classification fields (Category, Related System,
  Requested Priority) grouped; Summary and Description given full width; Attachments below;
  Submit/Cancel at the bottom; busy/success/error states per BR-19 to BR-21.
- **My Tickets**: search box, Category/Priority/Status filters, Clear Filters, Create Ticket
  action, sortable desktop table, mobile ticket cards, pagination, loading/empty/no-results/
  failure states.
- **Ticket Detail**: read-only ticket header fields, Attachments panel with add/download/
  remove actions and active/removed states, Back to My Tickets navigation.
- All screens use the Zen Green color tokens, one shared badge component for Requested
  Priority/Current Status, one shared field component with editable/read-only/error visual
  states, and the same loading/empty/error patterns.

## 7. Data Changes

New/changed Prisma models (see `server/prisma/schema.prisma` for the authoritative definition):

| Model | Purpose | Key fields |
|---|---|---|
| `Category` (existing, extended) | Fixed ticket categories | `+isActive Boolean @default(true)` |
| `RelatedSystem` (new) | Affected service/device/app | `id, name @unique, isActive, createdAt` |
| `RequesterUser` (new) | Development Requester (Lab 2 stand-in for a logged-in user) | `id, name, email @unique, isActive, createdAt` |
| `Ticket` (new) | One support request | `id, ticketNumber @unique, requesterId FK, categoryId FK, relatedSystemId FK, summary, description, requestedPriority enum, currentStatus enum (default NEW), createdAt, updatedAt` |
| `Attachment` (new) | One file on a Ticket | `id, ticketId FK, originalName, storedFilename, mimeType, sizeBytes, uploadedAt, removedAt?, removedReason?, removedById? FK` |

Enums:
- `RequestedPriority`: `LOW`, `MEDIUM`, `HIGH`.
- `TicketStatus`: `NEW`, `OPEN`, `IN_PROGRESS`, `PENDING`, `RESOLVED`, `CLOSED`, `CANCELLED` —
  the full lifecycle is modeled now so later labs need no breaking migration, but Lab 2 code
  paths only ever write and display `NEW`.

Relationships: `RequesterUser 1—N Ticket`, `Category 1—N Ticket`, `RelatedSystem 1—N Ticket`,
`Ticket 1—N Attachment`, `RequesterUser 1—N Attachment` (via `removedById`, optional — who
performed the soft removal).

Indexes: `Ticket.requesterId`, `Ticket.categoryId`, `Ticket.createdAt` (list sorting/filtering),
`Attachment.ticketId`. Uniqueness: `Ticket.ticketNumber`, `RequesterUser.email`,
`Category.name`, `RelatedSystem.name`.

Attachment file storage: local disk under `server/uploads/lab-02/<ticketId>/<storedFilename>`,
git-ignored. `storedFilename` is a generated UUID + extension, never derived from the uploaded
filename, so it cannot be used for path traversal or collide across Requesters.

## 8. API Contract

Full detail lives in `docs/lab-02/api-spec.md`. Summary of endpoints:

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/categories` | Active Categories |
| GET | `/api/related-systems` | Active Related Systems |
| GET | `/api/requesters` | Active Development Requesters (selector) |
| POST | `/api/tickets` | Create a Ticket for the current Requester |
| GET | `/api/tickets` | List the current Requester's Tickets (search/filter/sort/page) |
| GET | `/api/tickets/:id` | One owned Ticket, with its active+removed Attachments |
| POST | `/api/tickets/:id/attachments` | Upload one Attachment to an owned Ticket |
| GET | `/api/attachments/:id` | One Attachment's metadata (ownership-checked) |
| GET | `/api/attachments/:id/download` | Binary download of one **active** Attachment |
| DELETE | `/api/attachments/:id` | Soft-remove one Attachment (body: `reason`) |

All `Tickets`/`Attachments` endpoints require `X-Dev-Requester-Id`. Reference-data endpoints do
not (they are not owned data).

## 9. Acceptance Criteria

- AC-01 Given valid Ticket data, when the Requester submits the form, then one Ticket is saved
  and the official Ticket Number is displayed.
- AC-02 Given no Development Requester is selected, when the user attempts to open My Tickets,
  Create Ticket, or a Ticket Detail URL directly, then the Requester Selection screen is shown
  instead.
- AC-03 Given Requester B is selected, when a Ticket belonging to Requester A is requested (list,
  detail, or attachment), then the data is not returned (`404`).
- AC-04 Given the Summary field is empty, when the Requester submits, then a field-level message
  appears under Summary and no API call is made.
- AC-05 Given the Description is 10 characters, when the Requester submits, then a field-level
  "too short" message appears and no API call is made.
- AC-06 Given the backend is unreachable, when the Requester submits a valid form, then a safe
  failure banner is shown and every entered value is still in the form.
- AC-07 Given the Requester double-clicks Submit, when the first request is still in flight,
  then only one Ticket is created and the button is disabled/busy during that time.
- AC-08 Given a Requester has zero Tickets, when they open My Tickets, then the empty state with
  a Create Ticket action is shown (not the no-results state).
- AC-09 Given a Requester has Tickets but the search text matches none of them, when the list
  loads, then the no-results state with Clear Filters is shown.
- AC-10 Given a Requester searches by an exact Ticket Number, when the list loads, then only
  that Ticket is returned.
- AC-11 Given a Requester filters by Category, when the list loads, then only Tickets in that
  Category are returned.
- AC-12 Given more Tickets than one page, when the Requester opens page 2, then a different,
  correctly-ordered slice of their own Tickets is returned.
- AC-13 Given a Requester sorts by Created Date ascending, when the list loads, then the oldest
  owned Ticket appears first.
- AC-14 Given a valid JPG under 5 MB, when the Requester selects it as an Attachment, then it
  uploads and appears as an active Attachment.
- AC-15 Given a 6 MB PDF, when the Requester selects it, then it is rejected before/at upload
  with a clear size message and no Attachment row is created.
- AC-16 Given a `.exe` file, when the Requester selects it, then it is rejected with a clear
  type message and no Attachment row is created.
- AC-17 Given a Ticket already has five active Attachments, when a sixth is selected, then the
  upload is rejected with a clear "maximum reached" message.
- AC-18 Given an active Attachment, when the Requester clicks Download, then the original file
  content is returned.
- AC-19 Given a Requester removes an Attachment with a reason, when the removal completes, then
  the Attachment shows as removed with that reason, and Download/Preview are disabled.
- AC-20 Given a removed Attachment, when its download endpoint is called directly, then the
  server rejects it (`410`) rather than returning the file.
- AC-21 Given the Requester switches from Requester A to Requester B via Change Requester, when
  My Tickets reloads, then Requester A's Tickets are no longer shown.
- AC-22 Given the active-Requester list fails to load on the Selection screen, when the page
  renders, then a safe failure state with Retry is shown instead of a blank dropdown.
- AC-23 Given the viewport is under 768px, when any of the three main screens render, then no
  horizontal page scrolling occurs and all controls remain reachable and legible.
- AC-24 Given a screen reader or keyboard-only user, when they tab through the Create Ticket
  form, then every control is reachable, labeled, and shows a visible focus indicator.
- AC-25 Given the Ticket creation succeeds, when the confirmation is shown, then it displays the
  backend-issued Ticket Number and a clear next action (view the Ticket / back to My Tickets).
- AC-26 Given a Category or Related System id that does not exist or is inactive, when the
  Requester submits, then the Ticket is rejected with a field-level message and not created.
- AC-27 Given the `X-Dev-Requester-Id` header is missing or unknown, when any Ticket/Attachment
  endpoint is called, then the request is rejected without leaking whether the target resource
  exists.

## 11. Assumptions and Decisions

- **Identity transport**: a custom `X-Dev-Requester-Id` header (not a cookie/session) carries
  the selected Requester on every owned-data call. This keeps the mechanism visibly different
  from real authentication while still letting the backend enforce real ownership checks now,
  per BR-08/BR-33.
- **Ownership failures return 404, not 403**: so a Requester probing another Requester's Ticket
  id cannot even learn that the id exists (BR-13, AC-03, AC-27). An inactive/unknown Requester
  *identity itself* (not the target resource) returns `403`, since that failure is about the
  caller, not about leaking another Requester's data.
- **Ticket Number generation**: a dedicated PostgreSQL sequence (`ticket_number_seq`) rather
  than deriving from the row's primary key, so the value is assigned atomically before insert
  with no follow-up update statement and no transaction needed (BR-01).
- **IT Priority and Ticket Owner are out of scope**: the illustrative Figure 1/Figure 2 mockups
  in the handout show these fields, but they belong to the IT Staff workflow explicitly
  excluded from Lab 2 (§4.2 of the handout). My Tickets and Ticket Detail in this sprint show
  only Requester-relevant fields (Ticket Number, Created Date, Category, Related System,
  Summary, Requested Priority, Current Status, Last Updated).
- **Attachment storage**: local disk (git-ignored `server/uploads/lab-02/`) with DB-tracked
  metadata, rather than DB `bytea` storage, for simplicity and to keep the database small; the
  storage strategy is isolated behind a small module so it can be swapped for object storage
  later without changing the API contract.
- **Full `TicketStatus` enum modeled now, only `NEW` reachable**: avoids a breaking schema
  change when Lab 3/4 add workflow, at the cost of a slightly larger enum than Lab 2 strictly
  needs (documented as a deliberate forward-compatibility decision, per BR-02/§5.2 of the
  handout).
- **`Category`/`RelatedSystem` gain `isActive`**: not requested by name in the handout's minimal
  example schema, but required to make "retrieve active Categories/Related Systems" (§6 of the
  handout) a meaningful, testable query rather than always returning everything.
